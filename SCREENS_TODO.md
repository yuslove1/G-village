# Remaining screens/features

Checklist against the 45-screen design blueprint in `design_idea/GadgetHub_all_screens/`. Everything not listed here is built. Check items off as they land.

## Not built

- [x] **C5 — Filter sheet.** Built: `frontend/src/components/filter-sheet.tsx`, a Radix Dialog bottom sheet (condition, price-range slider, brand chips sourced live from `/catalog/products`, verified-only) with a live result count wired to the real `GET /catalog/listings`. Also added `verified` as a real query param on the backend — it was not actually supported despite being listed as already-there.
- [x] **B1 — Welcome / onboarding splash.** Built: `/welcome`, shown once per device via `frontend/src/lib/onboarding.ts` (localStorage flag) and `frontend/src/components/welcome-redirect.tsx` (redirects a first-run guest off `/`, same one-shot pattern as `StaffHomeRedirect`).
- [x] **C9 — Trade-in at checkout.** Built: `frontend/src/components/trade-in-panel.tsx`, wired into `/checkout`. Required a new backend endpoint, `POST /sales/trade-in-quote` — the existing `/sales/quote` returns the sell-flow's full cash offer, not the 7%-discounted credit `createOrder()` actually applies at checkout (see `lib/appraisal.ts`'s `tradeInCredit()`), so reusing it would have quoted a bigger credit than checkout could honour.

## Simplified — works, but not the full design

- [x] **7 — Dashboard.** `/account` now shows inline previews above the quick-links list: last 2 orders with status, an active sale if there is one, and the top 2 saved alerts — each with a real, live match count (see below), not the placeholder "No matches yet" it showed before. "Buyers interested" wasn't carried over — there's no such concept tracked anywhere (no view/interest model), so it would've been fabricated; real status is shown instead.
  - Added as a side effect: `GET /alerts` now computes an honest live `matchCount` per alert (query against current LIVE listings matching the alert's product/tiers/price) — there was no matching logic at all before this, so the alerts list page's "last matched" text was always empty. Both `/alerts` and `/account` use it now.
- [x] **B5 — Settings sub-pages.** Both halves built.
  - Notifications: `/account/notifications` — order updates, price alerts, marketing, each a real toggle backed by new `notifyOrderUpdates` / `notifyPriceAlerts` / `notifyMarketing` booleans on `User` (migration `20260812235928_add_notification_preferences`), read/written via `GET /auth/me` and the new `PATCH /auth/notifications`.
  - Payment methods: `/account/payment-methods`, list/set-default/remove against a new `SavedCard` model (migration `20260813002947_add_saved_cards`). A card is captured automatically the first time someone pays by card and Paystack reports the authorization as reusable — there's no manual "add card" flow, since a card can only ever come from an actual successful charge. `authorizationCode` (the Paystack token that lets us charge it again) is never serialised to the client anywhere — verified this by inspecting every response from the new routes. Checkout's `/orders/[reference]/pay` now offers saved cards ahead of the channel picker; paying with one calls Paystack's charge-authorization API directly (no redirect) and re-verifies with `verifyTransaction()` before marking anything paid, same trust rule as every other payment path here. Verified live end-to-end against a real user: seeded/patched/deleted test rows through the actual endpoints (ownership isolation, default-swap exclusivity, no auth-code leakage), migration applied cleanly. Did not drive an actual Paystack test-mode charge (needs their hosted checkout or OTP simulation) — the capture path is code-reviewed against Paystack's documented response shape but not exercised live.
- [x] **F3 — Payment failed.** Consolidated onto one screen: `/orders/[reference]/confirm`'s failure state now shows the live reservation countdown and lets you retry inline with an alternate payment channel (excludes whichever channel just declined), instead of pointing to the separate `/pay` page.

## Post-launch improvements (not from the original 45-screen list)

- [x] **Staff navigation.** Admin/agent had two real bugs: clicking "Marketplace" from `StaffTopBar` stranded staff on the consumer site with no way back, and the avatar there wasn't clickable. Fixed: `TopNav`/`BottomNav` now show a role-aware "Dashboard" link/FAB for ADMIN/AGENT accounts (desktop pill next to "Sell a gadget"; mobile FAB swaps from Sell to Dashboard, since Sell isn't the useful action for staff browsing the marketplace), and the `StaffTopBar` avatar now links to `/account`.
- [x] **Agent dashboard.** Was just a bare queue list. Added real stat tiles (completed today/this week, assigned to you, open for claim) via a new self-scoped `GET /admin/agents/me`.
- [x] **Admin panel: tables + delete.** `/admin/stock`, `/admin/vendors`, `/admin/agents`, `/admin/orders` now render a real `<table>` at the `lg:` breakpoint (mobile keeps the card list — a table at 375px is just clipped columns) with delete/remove actions: withdrawing a listing (`PATCH .../status = WITHDRAWN`, the field already existed), removing a vendor (`DELETE /admin/vendors/:id`, soft via `isActive`), removing an agent (`DELETE /admin/agents/:id`, soft via `User.deletedAt`, reassigns their open queue back to the open pool rather than orphaning it). No delete on orders — a real order is a financial record, not something a UI button should be able to erase.
- [x] **Customizable inspection checklist.** New `/admin/checklist` page lets admin add/remove extra checklist items agents see during a device review, on top of the six fixed ones (which stay in code — two of them hard-block approval and aren't something a UI should be able to loosen). New `ChecklistItem` + `InspectionChecklistResult` models (migration `20260813012908_add_checklist_items`), wired into the existing `POST /admin/inspections/:reference/complete` as an additive `checklistResults` array — approval/grading/ledger logic is untouched.

## Gaps closed after a functionality audit against design_idea/GadgetHub_all_screens

An independent audit (agent, not this file) found 8 screens with real functional gaps behind an otherwise-complete build. All closed:

- [x] **S8 — Payout / A1 — Payouts due.** There was no way for money owed to a seller to actually leave the business — `SaleStatus.PAID` existed in the schema but nothing ever set it. Built: real Paystack Transfer integration (`createTransferRecipient`/`initiateTransfer` in `lib/paystack.ts`), a `Payout` model tracking each withdrawal PENDING → SUCCESS/FAILED, and a `transfer.success`/`transfer.failed` webhook handler (`payout.service.ts`) that only reduces the seller's ledger balance and flips their sales to PAID once Paystack confirms — never on the initiating request, same trust rule as card payments. `POST /payouts/accounts` now verifies the bank account against Paystack (`resolveAccount`) and registers a transfer recipient before saving it, instead of trusting whatever the seller typed. `/sell/payout` gets a real Withdraw button + recent-payouts list; `/admin/payouts` is a new page listing who's owed money (visibility only — the seller withdraws their own money, admin doesn't move it for them).
- [x] **D4 — Admin agents.** No way to add an agent existed; the only path in was seeding the database directly. Built: `POST /admin/agents` (admin or agent role, temp password returned once since there's no SMS/email provider to deliver it) + `/admin/agents/new`. Also added a derived Active/Onboarding status pill (zero inspections ever = onboarding), matching the design.
- [x] **A1 — Admin overview "Needs your action".** Was entirely unbuilt. `GET /admin/overview` now returns a real `actions` list: paid orders awaiting vendor-sourcing confirmation, today's booked inspections, and approved direct sales still owed a payout — each linking straight to where it gets resolved.
- [x] **6 — Receipt PDF export.** No PDF generation existed anywhere in the codebase. Built with `pdfkit`: `GET /orders/:reference/receipt.pdf`, wired to a real "Download PDF" button.
- [x] **C6/C7 — Alerts.** Match counts were real and live but nothing ever notified anyone — no email/SMS/push provider existed. Built email delivery via Resend (`lib/email.ts`, optional — unset `RESEND_API_KEY` just logs instead of sending): fires when a listing goes LIVE (all three paths — direct publish, status PATCH, inspection approval), checked against each active alert's product/query/tier/price filters, `lastFiredAt` now actually gets set. SMS/push explicitly out of scope for this pass (no provider chosen yet).
- [x] **B2/B4 — Google sign-in.** Built full OAuth flow (`lib/google.ts` + `/auth/google`, `/auth/google/complete`) against `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, which are unset placeholders in `.env` — the button doesn't render on the frontend until `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is set to a real Google Cloud OAuth client. A returning user (matched by verified email) logs straight in; a first-time Google identity gets a 10-minute signup token and one extra screen asking for a phone number, since this app's identity model is phone-first and Google never provides one.

All of the above: backend `tsc --noEmit` clean, frontend `next build` clean, smoke-tested live against the real dev database (agent creation + login with generated password, admin overview/payouts endpoints, PDF bytes verified as a real `%PDF-` stream). Paystack-dependent paths (bank verification, transfer initiation) are code-reviewed against Paystack's documented API shape but not exercised against a live transfer, same caveat the card-payment integration already carries — this repo's `PAYSTACK_SECRET_KEY` is a placeholder test value, not a real key.
